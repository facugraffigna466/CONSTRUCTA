## When to use this skill

- A teacher or collaborator proposes a new data model or schema change
- You need to evaluate whether a proposed model change is safe to apply
- You need to audit alignment between `backend/app/models/`, `backend/app/schemas/`, and `frontend/src/types/index.ts`
- Alembic migrations are needed for model changes
- You are classifying changes as SAFE, FUTURE, or REJECTED

## Classification framework

Every proposed change must be classified before touching any file:

### SAFE — Apply now
- Additive changes: new nullable column, new relationship
- Changes that don't break existing queries
- Aligning `ObraSummary` / `TaskRead` with missing frontend fields
- Adding a new optional field to a `Read` schema

### FUTURE — Defer intentionally
- Requires multi-step migration
- Requires coordination with chatbot pipeline
- Alters existing status machine or transitions
- Requires WhatsApp flow changes (e.g., adding new `MessageType`)
- High risk of breaking existing features if applied partially

### REJECTED — Do not apply
- Removes existing fields that the frontend or chatbot use
- Changes the meaning of a foreign key relationship
- Bypasses the current layered architecture
- Introduces premature abstraction or out-of-scope complexity
- Breaks the chatbot identity key (`whatsapp_number`)

## Alignment audit checklist

When checking if backend and frontend are aligned, verify each entity:

| Entity | Backend model | Backend Read schema | Frontend type | Aligned? |
|---|---|---|---|---|
| Obra | obra.py | ObraRead | `interface Obra` | — |
| Task | task.py | TaskRead | `interface Task` | — |
| Responsible | responsible.py | ResponsibleRead | `interface Responsible` | — |
| Alert | alert.py | AlertRead | `interface Alert` | — |
| HistorialEvento | historial.py | HistorialEventoRead | `interface HistorialEvento` | — |

For each field in the `Read` schema, verify the frontend `interface` has the same field with the correct TypeScript type:

| Python type | TypeScript type |
|---|---|
| `str` | `string` |
| `str \| None` | `string \| null` |
| `int` | `number` |
| `int \| None` | `number \| null` |
| `bool` | `boolean` |
| `date` | `string` (ISO date YYYY-MM-DD) |
| `datetime` | `string` (ISO timestamp) |
| `ObraStatus (enum)` | `ObraStatus (union of string literals)` |
| `dict / JSON` | `Record<string, unknown>` |

## Rules to respect

### Never blindly apply a proposed model
Every change must be evaluated against the running system. A professor/teacher proposal is a reference, not a command.

### Additive-first principle
Prefer adding new nullable columns over renaming or removing existing ones.
Existing data and queries are not broken by nullable additions.

### Migrations are mandatory for DB schema changes
Any change to a SQLAlchemy model must have a corresponding Alembic migration.
Enum value additions require explicit SQL:
```sql
ALTER TYPE taskstatus ADD VALUE 'new_status';
```
This cannot be auto-generated by Alembic — write it manually in the migration file.

### Frontend types must stay aligned with Read schemas
After any schema change, update `frontend/src/types/index.ts` to match.
The frontend does NOT generate types from the backend — they must be manually synchronized.

### Chatbot pipeline is most fragile
Changes to `Task.status`, `TaskStatus` enum values, `VALID_TRANSITIONS`, or `Responsible.whatsapp_number` may break the chatbot pipeline.
Any change here must be explicitly approved and tested via the webhook flow.

### ObraSummary must include fields that frontend uses
`ObraSummary` is used for the list endpoint (`GET /obras`). If the frontend's `Obra` type uses a field (e.g., `actual_end_date`), `ObraSummary` must include it.

## Step-by-step process

### Step 1 — Read the proposed model

Understand what the proposal adds, removes, or changes.
Do not start classifying until you have read the full proposal AND the current state of all affected files.

### Step 2 — Classify each change

For each proposed change:
1. Identify the affected model, schema, and frontend type
2. Classify: SAFE / FUTURE / REJECTED
3. Write the reason for the classification

Template:
```
Change: Add `priority` field to Task
- Current: not in model, schema, or frontend type
- Classification: SAFE (additive, nullable, no impact on existing data)
- Action: Add to Task model, TaskRead schema, TaskUpdate schema (optional), frontend Task interface

Change: Remove `estimated_progress` from Task
- Current: used in ResumenTab for progress bar, populated by AI pipeline
- Classification: REJECTED (breaks frontend StatCard, breaks Phase 2 pipeline)
- Action: Keep as-is
```

### Step 3 — Apply SAFE changes only

For each SAFE change:

**Backend model** (`backend/app/models/<entity>.py`):
```python
priority: Mapped[int | None] = mapped_column(Integer, nullable=True, default=None)
```

**Backend schema** (`backend/app/schemas/<entity>.py`):
- Add to `<Entity>Read`
- Add to `<Entity>Update` only if it should be user-editable
- `<Entity>Create` only if it's required at creation

**Frontend type** (`frontend/src/types/index.ts`):
```ts
interface Task {
  // ...existing fields...
  priority: number | null;
}
```

**Migration**:
```bash
cd backend && alembic revision --autogenerate -m "add priority to tasks"
cd backend && alembic upgrade head
```

### Step 4 — Document all decisions (SAFE/FUTURE/REJECTED)

Document every classification in `documentacion.md`, not just the changes applied.
This provides the rationale for future sessions to understand why certain changes were deferred.

## Validation commands

```bash
# 1. Backend imports OK after model changes
cd backend && python3 -c "from app.main import app; print('imports OK')"

# 2. Migration applied correctly
cd backend && alembic current
cd backend && alembic upgrade head

# 3. Frontend types aligned
cd frontend && npm run build

# 4. API still works
# Start server and test GET/PATCH on affected endpoints
```

## Common mistakes to avoid

| Mistake | Consequence | Fix |
|---|---|---|
| Applying a proposed model change without reading current system first | Breaks running features | Always read all affected files before classifying |
| Renaming existing fields | Breaks all queries and frontend mappings | Prefer additive over renaming |
| Adding non-nullable column without migration default | DB error on `alembic upgrade head` | Always use `nullable=True` or provide `server_default` |
| Updating `TaskRead` but not `frontend/src/types/index.ts` | TypeScript type mismatch (may not catch at build if field is optional) | Always sync both |
| Adding `status` to `TaskUpdate` | DR-01 violation | Use `TaskStatusUpdate` (internal only, never exposed) |
| Changing enum values without Alembic explicit migration | DB error on enum insert | Write `ALTER TYPE` manually in migration file |
| Applying FUTURE changes without approval | Risk of partial breakage | Document as FUTURE, defer until explicitly requested |
